## 1. Structure summary (each detail verified against §-text)

**Five sections, fixed order** (§3, `:40-56`): 292-byte header (offset 0) → tile index (20 × tile_count at `index_offset = 292`, normative via §4.11/`#25`) → 0–3 zero pad to 4-alignment → tile blob (each tile 4-aligned, `tile_blob_start = align4(292 + 20·tile_count)`, `:65`) → TLV extension sections at `extensions_offset` → 4-byte CRC-32/ISO-HDLC footer (§10, scope = bytes [0, size−4), check value `0xCBF43926` for "123456789"). Pack ≤ 2³²−1 bytes; all offsets u32 LE (`:58`).

**Header offsets confirmed** (§4 table, `:72-97`): magic `RAWT`@0, version (1,0)@4, `reserved_v1_0`@6, pack_uuid@8, supersedes_uuid@24, parent_uuid@40 (must be zero), enums pixel_format/projection/addressing/axis @56–59, tile_dim_px u16@60 (non-zero), zoom_min/max@62/63 (`zoom_max < 24`), bbox 4×i32 microdegrees @64–79, build_timestamp u64@80, tile_count@88, index_offset@92, **zoom_offsets[24]** (24 × 8-byte {offset,count}) @96–287, extensions_offset@288. 96+192+4 = 292 exactly; alignment argument at `:60`.

**Index entry (20 B)** (§5.1, `:200-212`): z u8, compression u8, flags u8 (=0), reserved u8 (=0), x u32, y u32, offset u32, length u32. Sorted (z, x, y), strict within-zoom; lookup = zoom_offsets[z] guard (z ≥ 24 → absent, count == 0 → absent) then binary search (§5.3, `:228-233`).

**Pixel formats** (§8.1, §9): ABGR2222 = 1 (1 B/px, A in top 2 bits, writers set A=3) and RGB565 = 2 (2 B/px, LE on disk, R5 bits 15–11); values 0, 3–255 reserved → reject. **Compression** (§8.5): None = 0, RLE = 1 (pixel-level, §9.11); 2 (QOI), 3 (LZ4), 4–255 reserved → reject.

**Legal pairs** (§8.6, `:431-436`): only (WebMercator, Quadtree) and (LocalLinear, SingleImage). SingleImage: tile_count == 1, lone entry (0,0,0), zoom_min = zoom_max = 0, axis = XYZ, zoom_offsets[1..23] zero. AFFN (48 B, six f64, finite, +0.0 only) exactly-once iff LocalLinear (§7.3). Axis XYZ = 1 / TMS = 2 (§8.4). Quadtree tile_count == 0 metadata-only packs legal (§8.6).

**pack_uuid canonical derivation** (Appendix A): `UUIDv5(4e72f962-6632-4538-8e0a-7eab63350f3f, JCS(descriptor))` (§A.1–A.2, `:928-939`); descriptor keys `affn, bbox, format_version, pixel_format, projection, quantiser_version, sources, style_hash, tile_addressing_scheme, tile_axis_convention, tile_dim_px, zoom_range` (§A.3 table, `:960-973`); microdegrees via banker's rounding with worked tie examples (`:948-952`); sources sorted by (zoom_min, zoom_max, kind, identity) (§A.4); worked example incl. intermediate SHA-1 for bisecting mismatches (§A.5, `:1040-1052`). `golden-canonical-uuid` generator self-tests the A.5 example end-to-end (CONFIRMED in `generators/golden_canonical_uuid.py`).

**Eager-vs-lazy model** (§11.1–11.2): one conformance level; timing is per-reader. Eager subset = header rules + open-time O(tile_count) index walk enforcing #18 padded-sum and #32 tight layout with one u32 accumulator (`:620`); lazy subset = per-tile/per-extension/AFFN rules (table `:596-616`). Byte-leak prohibition `:588`. The **~1 KB claim** (`:582`): "292 B header + 192 B (within the header) zoom directory + ~64 B scratch + decoder state (≤ 8 B for RLE …) → structural-reader working memory ≤ 1 KB, plus whatever pixel buffer the renderer chooses". Arithmetic checks out (the 192 B is inside the 292; ~360 B + row buffer).

## 6. Limits stress

- **u32 offsets / 4 GB pack ceiling** (§3, `:58`): first real break = offline country/metro pack at street zoom. 256 px RGB565 tile raw = 131,072 B; at the claimed 27%-of-raw RLE ≈ 35.4 KB + 20 B index ⇒ ~121,000 tiles max per pack. z15 tile ≈ 1.22 km/side at the equator → ~180,000 km² ceiling (equator), ~90,000 km² at 45°N. A z15 city pack fits easily (Greater Tokyo ≈ 10 k tiles); **Italy at z16 needs ≈ 1.5 M tiles ≈ 52 GB — 13× over**; even a single z18 metro layer (Greater London ≈ 2,300 km², z18 tile ≈ 0.036 km² at 51°N) ≈ 64 k tiles ≈ 2.3 GB for that layer alone, so z6–z18 full-pyramid London already brushes the ceiling. Not binding for the motivating 200 KB-flash wearables; binding for the spec's own "kiosks, e-readers" audience (`:13`). No multi-pack/sharding story in the spec.
- **24-entry zoom directory** (§4.12): z23 ≈ 1.87 cm/px at 256 px — beyond OSM (z19) and Google (z21–22) raster. First break: cm-GSD drone orthomosaics (0.5–1 cm/px wants z24–25), which the format would instead push to SingleImage. Verdict: never binding for slippy-map content; effectively a non-limit.
- **16-bit tile_dim_px** (§4.7): 65,535 max. The sharper constraint is that **SingleImage images must be square** (§4.9 `:153`: "W = H = tile_dim_px") — a 2:1 scanned map must be padded to a square, up to 2× (aspect-ratio²) byte waste before RLE. Interplay with the 4 GB ceiling: max uncompressed SingleImage = 65,535² × 1 B = 4.2949 GB → fits with 300 B to spare for ABGR2222 (just), but RGB565 caps at ~46,340 px square. First break: A0 sheet at 1200 dpi (56 k × 40 k) as RGB565 → pad to 56 k² → 6.3 GB > 4 GB. Realistic floor plans (10 k px class) are fine.
- **Microdegree bbox** (§4.9): 1 µ° ≈ 0.111 m latitude. Rendering never uses bbox for SingleImage — AFFN carries f64 georeferencing — so the 11 cm quantum only affects pack *selection/metadata*: a 30 m floor plan's bbox is good to ~0.4%. Fine. The consequential microdegree issue is not precision but reproducibility: the ≤ 1 µ° libm slack (`:151`) feeding pack_uuid (finding #4).

## 7. Quantization / interop (§9.1.1)

Normative language, quoted: §9.1.1 `:480` — "The quantisation is integer-only by construction: any conforming implementation MUST produce byte-identical output for the same input across architectures, languages, and platforms." Thresholds are exact integer ranges (0–42→0, 43–127→1, 128–212→2, 213–255→3) pinned by the §14.4 test vector and `quantiser_version = 1`. §9.2.1 likewise: pure bit-truncation, "integer-only by construction", §14.7 vector, and even the decode direction is pinned (bit-replication MUST, `:515`). **Judgment: the quantisers are specified tightly enough — byte-identical across independent writers, no float, no ambiguity.** But quantiser tightness is necessary, not sufficient, for pack_uuid-reproducible byte-identical *tiles*: the RGB888 input to the quantiser comes from an implementation-defined pipeline (§A.4 `:1002`: "The spec does NOT prescribe a specific decode/resample/alpha pipeline"), and the header bbox admits ±1 µ° libm drift (§4.9). Two independent writers produce byte-identical packs only when fed identical pre-quantise RGB888 and running bit-identical libm — i.e., the reproducibility contract is same-pipeline, not cross-implementation (finding #4).

## 8. v1.0 gate

Exact criterion, `spec/rawtiles.md:9`: "**v1.0 stabilizes the wire format once a second independent consumer has validated against this spec**; until then, fixtures and on-disk packs are not guaranteed forward-compatible."

Assessment: the only consumers today are (a) the same-author reference reader in the same repo — built alongside the spec, by the spec's author, with the conformance corpus as its own test suite — and (b) the same author's SDK reader. Neither is "independent" in any useful sense: both share the author's mental model, so they cannot catch the class of bug the gate exists for (ambiguous prose that two people read differently). Evidence the gate is doing no work yet: the reference reader currently *fails* 13 must-reject fixtures and still calls itself conformant. In spirit, the gate needs: a reader written by someone else, from the spec text alone (no reading the reference C), in a different codebase/community (InfiniTime, wasp-os, Bangle.js — the exact projects v0.4 names as motivation at `:1063`), passing the full negative corpus and the §14.5 per-tile hash tables — plus, ideally, a second *writer* reproducing `golden-canonical-uuid` byte-identically, since the dedup contract is the format's headline promise. A second same-author reader satisfies the letter only.

## 9. The RLE design (§9.11)

Decode algorithm (`:525-538`): stream of 1-byte headers `H`; bit 7 = 0 → literal run of `(H&0x7F)+1` pixels, payload `(H+1)·P` bytes copied verbatim; bit 7 = 1 → repeat run, payload exactly one `P`-byte pixel written `(H&0x7F)+1` times. Runs are 1–128 **pixels**, never split a pixel; no terminator — decode stops at exactly `tile_dim_px²·P` output bytes; under- or over-production is a per-tile error (§6.2 `:260`). Canonical encoder (`:542-547`): greedy, repeat threshold n ≥ 3 (n = 2 deliberately literal), literals merged, 128-cap splits. Worst-case expansion ≈ 0.78% (ABGR2222) / 0.39% (RGB565) (`:549`); max decompression ratio is bounded (~64–85×) and the output size is known from the header before decoding — no unbounded-bomb risk.

O(P) state claim (`:551`): header byte + run counter + P-byte repeat buffer + cursor, "≤ 8 bytes total" — **CONFIRMED as arithmetic** and matched by the reference decoder (`src/rawtiles.c:832-877`: `h`, `n_pixels`, `pixel[2]`, cursors).

27%-of-raw claim: Appendix B v0.6 (`:1065`): "Empirical measurement on the `stanley.rawtiles` corpus (12 tiles, zooms 12–14): byte-RLE on RGB565 → 90.0% of raw; pixel-RLE on RGB565 → 27.0% of raw (3.7×)." **PLAUSIBLE only**: the stanley corpus is not in the repo, the sample is 12 tiles from one area, and no RLE fixture exists to spot-check. Treat 27% as a single-corpus anecdote, not a spec property.

Per-row/streaming decode within a few KB: **genuinely possible per spec** — runs may cross row boundaries, but a decoder can suspend mid-run holding only the P-byte repeat pixel and a remaining-count, so row buffer (tile_dim·P: 512 B at 256 px RGB565) + ≤ 8 B state suffices; a 256 KB-RAM device is comfortable, and even 64 KB targets work row-streamed. Caveats: the spec's own justification sentence (`:551`, the "which never occurs" parenthetical) is muddled — it argues run boundaries align with rows, which is false (a 128-pixel run in a 64-px-wide tile spans rows); the *conclusion* (row-streamable) is right for the mid-run-suspend reason, not the stated one. And no implementation demonstrates it: the reference reader only decodes whole tiles into a caller buffer (131 KB at 256 px RGB565).

## 10. Security posture

What a reader MUST reject: the 38-rule checklist of §11.6 (`:650-690`) — short files, bad magic, major ≠ 1, zero pack_uuid, non-zero parent_uuid, every reserved enum byte, illegal projection×addressing pairs, zero tile_dim, zoom-range violations, bbox range/order, per-entry flags/reserved/order/bounds/length, zoom_offsets consistency, extensions_offset arithmetic, section framing/tags/duplicates, AFFN shape/finiteness, NAME/SRCD/ATTR text rules, CRC mismatch, index_offset ≠ 292, file > 2³²−1, x/y ≥ 2^z, tile-blob gaps/overlaps, non-zero padding. Overflow-discipline is explicitly engineered: §11.5 division-form tile_count fit check with the wrapping formulation banned (`:646`); #14's (c)-before-(d) ordering to avoid u32 underflow (`:665`); #19's subtraction-form section bound (`:670`); §5.3's z ≥ 24 guard against caller-controlled OOB (`:230`). The byte-leak prohibition (`:588`) forbids returning bytes whose protecting rule hasn't fired and requires zeroing/invalidating partial row-buffer output.

Does eager validation bound MCU memory? **Yes for structural state — the ~1 KB claim traces cleanly.** The eager subset needs: the resident 292 B header (zoom directory included), a 20 B entry scratch + previous-entry key for the #12–#17/#31/#32 walk, one u32 padded-length accumulator for #18/#32 (`:620`), and streaming CRC state (4 B + a chunk buffer of the implementation's choosing). That is a few hundred bytes; the reference reader's handle is ~330 B (README) with a 1 KB CRC chunk buffer. Unbounded-ish corners: (1) #29 NAME duplicate-locale detection over N sections needs either an unbounded seen-set or O(N²) re-reads — the spec quietly handles this by making #29 lazy and exempting readers that never enumerate sections (`:610`), leaving O(N²) I/O as the bounded-memory path; (2) the pixel/row buffer is excluded from the 1 KB by construction ("plus whatever pixel buffer the renderer chooses", `:582`) and a hostile header can declare tile_dim_px up to 65,535 (row = 128 KB, decoded tile = 8.6 GB for RGB565+RLE since #16 doesn't bound compressed entries) — the defense is §11.4's operational-refusal path (`:642`), which is adequate but means "opens successfully on a host validator" does not imply "renderable on the watch". Overall: unusually careful security posture for a hobby-scale spec; the residual risks are resource-exhaustion-by-declared-dimensions (mitigated by up-front refusal) and the untested RLE/RGB565 code paths (finding #1), not memory-safety holes in the validation model itself.
