## Ranked top findings (by consequence)

1. **The tutorial's on-device story does not exist.** No mechanism ships a `.rawtiles` pack to the watch — the `.uapp` container has no data slot at all (§6) — the entire pack-loading path is compiled out on hardware (§4.2), the Container reads via `std::fopen` rather than the SDK filesystem (§1.4), and a 787 KB whole-pack-in-RAM design cannot fit the 600 K GUI-process linker budget that must also hold TouchGFX heap and stacks (§7, §12). On hardware the map screen renders a slate rectangle. All CONFIRMED.
2. **`SDK::RawTiles::Container` is SDK-namespace, SDK-source-tree, cmake-wired production code with zero host-test coverage** (§3) and its only checker (`rawtiles_check`) is wired into no CI (§2). The only validation evidence is a dev tool that requires a `.hashes` sidecar produced by a tool that does not exist (§14).
3. **The pack generator (`slippypack`) and the format spec are both unverifiable from this repo.** `slippypack` exists nowhere — not on the branch, not on main, not on `$PATH` (§14). The spec the reader is written against lives in a personal external repo (`github.com/tobymurray/rawtiles`, "spec v0.2") — the ~40 `§ 11 #N` rule citations in Container.cpp cannot be checked against anything in-tree (§1.1).
4. **The TouchGFX workaround/bug mismatch is real, and intra-branch** (§10): `DynamicBitmapDraw.hpp` is gated `#if defined(SIMULATOR) && defined(__linux__)` (line 110) while the same branch's bug report documents the Y-clipping defect as "Reproduced on Windows simulator (MSVC), Linux simulator, and STM32U595 hardware" (`Docs/touchgfx-drawpartialbitmap-y-clipping-bug-report.md:36` @ ff098549) — the only in-tree mitigation is compiled out on the platform the bug is documented on, and nothing anywhere addresses the Y-overhang defect at all. CONFIRMED via `git show` on the refs.
5. **Container's validation logic itself is unusually strong** (§1.3) — the one genuinely well-engineered artifact here. All pointer arithmetic served after `open()` is pre-validated with overflow-safe u64 comparisons; I found no exploitable bounds bug. Caveats are minor (§1.5).
6. **The map never sees GPS** (§4.5): there is no Mercator/lat-lon→tile math anywhere in the app; the viewport centre is the pack's first index entry at `zoom_max`. "Tile-based map renderer" currently means "static 2×2 quadrant viewer of a bundled pack".
7. **ARCHITECTURE.md is stale twice over** (§4.4): byte-identical to GpsTrack's, which is itself verbatim Sensors-tutorial text; duplicate MyST anchor in three files; neither new tutorial is registered in `Docs/index.rst`.
8. **A PR today would dodge the strictest CI gates but not review culture** (§4.6, §13): the reproducible-build gate only covers `Examples/Apps`, tutorials-ci would auto-discover and ARM-build both new apps, and at 405 files the PR exceeds CodeRabbit's auto-review limit — while the human reviewer's track record on contract PRs is deep, adversarial line-level review.

## 1. `SDK::RawTiles::Container`

Files: `WT/Libs/Header/SDK/RawTiles/Container.hpp` (249 lines), `WT/Libs/Source/RawTiles/Container.cpp` (629 lines). Total 878 LOC. Author header dated 15-05-2026 (Container.hpp:4), committed 2026-08-01 in `7fc2602c`.

### 1.1 Spec pinning — CONFIRMED, with a consequence
Container.hpp:8-10: implements "the on-disk format defined at `https://github.com/tobymurray/rawtiles` (spec v0.2, wire format v1.0)". Container.cpp:8-9 repeats it. Every rejection rule is cited as `§ 11 #N` against that document. **The spec is external and personal** — nothing in either repo carries a copy, so none of the rule citations (`#1`–`#32` appear) are verifiable in-tree. The docstring (Container.hpp:12-13) claims enforcement of "#1–#19, #25, #30, #31", but the implementation also enforces #20, #23, #24, #27, #28, #32 (Container.cpp:339, 435-458, 517, 499-508, 469-478, 386-388) — the header undersells the code; doc drift either way.

### 1.2 Enums, API surface, memory model — CONFIRMED

- Other enums: Projection {WebMercator=1, LocalLinear=3} (hpp:42-45), Addressing {Quadtree=1, SingleImage=2} (hpp:50-53), Axis {XYZ=1, TMS=2} (hpp:58-61). Only two legal projection×addressing pairs (Container.cpp:98-102).

Each carries a `§ 11` citation in both the enum comments and `describeResult()` (Container.cpp:597-626).

### 1.3 Validation rules actually enforced — CONFIRMED (traced line by line)
`parseAndValidate()` (Container.cpp:169-523) enforces, in order: min size 296 (175), magic `RAWT` (180), major==1 (187), pack_uuid≠0 (194), parent_uuid bytes 40..55 ==0 (199), enum bytes 56-59 whitelisted (210-221), legal enum pair (228), tile_dim_px≠0 (234), zoom_max<24 && zoom_min≤zoom_max (241), bbox in ±180e6/±90e6 µdeg and non-inverted (250-265), index_offset==292 (272), **tile_count bounded by file size before it is trusted** (281-284: `indexCapacity = (size − 296)/20`), extensions_offset 4-aligned / ≤ size−4 / ≥ tile_blob_start (305-313). The index walk (327-410) then enforces per-entry: compression==0, flags==0, reserved==0, zoom_min≤z≤zoom_max, x,y < 2^z for Quadtree, strict (z,x,y) ascending order, offset 4-aligned, offset within [tile_blob_start, extensions_offset), `offset+length ≤ extensions_offset` computed in uint64 (382), **offset must equal the running tight-layout expectation** (386-388), and `length == tile_dim_px²` (390-394). Post-walk: extensions_offset must equal the walked end (413), the 24-entry zoom directory must match walked counts and first offsets exactly (418-432), SingleImage packs must have exactly one z0/x0/y0 tile (435-458), extension sections are framing-validated with overflow-safe bounds, zero padding, printable tags, and unknown *upper-case* tags rejected (462-514), and the pack must end exactly at the CRC footer (512). Finally CRC-32/ISO-HDLC over everything but the last 4 bytes (516-531).

### 1.4 Pointer-arithmetic safety — CONFIRMED sound, no bounds bug found
This was audited adversarially:
- Every pointer later served (`getTile`, `getTileByIndex`) derives from index entries that were fully bounds-checked at open; `getTile`'s binary search (Container.cpp:549-569) reads only within `dir.offset + dir.count*20`, and `dir.offset`/`dir.count` were proven consistent with the walked index (418-432), so entry reads and the returned `base + off / len` view are in-bounds by construction.
- `getTile` guards `z >= 24` before indexing `zoomOffsets` (540-542); `getTileByIndex` guards `i >= tileCount` (575).
- Arithmetic that could overflow is done in uint64: index bytes (297), blob start (298), `offset+length` (382), `expectedLen` (390), and `align4` cannot overflow for `length ≤ 65535²` (max 4,294,836,228 < 2³²... note 4294836225+3 = 4294836228 < 4294967296 — safe).
- Extension walk bounds: `length > crcStart − pos − 8` and `paddedLen > crcStart − pos − 8` (483-489) prevent both overflow and overrun; padding bytes are read only inside that bound (491-495).

Verdict: the reader's bounds discipline is genuinely strong — better than most of what already ships in `Libs/Source`. That makes the *zero test coverage* (§3) more anomalous, not less: the code makes ~40 distinct rejection claims and not one is exercised by a test in-tree.

### 1.5 Minor defects — CONFIRMED
- **CRC table init is racy**: `static uint32_t table[256]; static bool tableReady;` guarded by a plain bool (Container.cpp:77-88) — not a magic static; two threads opening containers concurrently race the table fill. Benign result values in practice (idempotent fill) but formally UB (data race).
- `describeResult(BadEnum)` says "§ 11 #7" (Container.cpp:607) but `BadEnum` is also returned for a bad per-tile compression byte (339-341), which the hpp attributes to the tile-index domain — small mislabel in diagnostics.
- `long sz = std::ftell(f)` (Container.cpp:119) — on an LP32 host a >2 GB file returns −1 and is caught (120-123); fine, noted only for completeness.
- `openFromMemory` copies the buffer (`mBytes.assign`, 154) — doc says "copied into the container" (hpp:189), consistent.
- Move ctor/assign defaulted (hpp:177-178): safe — `TileRef`s point into vector storage, which is stable across vector move.

## 4. The RawTilesMap app (`WT/Docs/Tutorials/RawTilesMap/`)

### 4.1 TileCanvas — CONFIRMED
`gui/include/gui/map_screen/TileCanvas.hpp` (43 lines) + `gui/src/map_screen/TileCanvas.cpp` (91 lines) = **134 LOC**. A `touchgfx::Widget` holding `BitmapId mIds[9]` (`kGrid=3`, `kCells=9`, hpp:23-24). Draw path (cpp:23-91): fills the dirty rect with a "sentinel slate" colour first (cpp:28-30, so missing tiles show the pack's bbox rather than garbage), anchors the grid so the seam shared by cells (1,1),(2,1),(1,2),(2,2) lands at widget centre — "With 256-px tiles on a 240-px widget each of those four cells exposes one quadrant" (cpp:42-46; hpp:11-15 says the outer five cells are "loaded but off-screen until panning (future step)"). **Zero-copy is real**: pixels come from `Bitmap::dynamicBitmapGetAddress(id)` (cpp:69) over buffers registered with `dynamicBitmapCreateExternal` pointing directly at pack bytes (Model.cpp:173-175, comment at 99-104: "tile bytes are referenced in-place … no pixel copy, no large BSS pool"). Rendering uses **`HAL::lcd().blitCopy`** with a manually pre-clipped, source-relative blitRect (cpp:75-88), explicitly to route around the TouchGFX `LCD8bpp_ABGR2222::drawPartialBitmap` defect (comment cpp:48-54 cites the investigation bundle, §11).

### 4.2 Model.cpp — CONFIRMED simulator-only, env-var hack present
`gui/src/model/Model.cpp` (338 lines). **The entire pack path is inside `#if defined(SIMULATOR)`** — both the include/candidate-path block (lines 12-35) and the whole open/viewport/bitmap-registration block in the constructor (lines 44-188). There is no `#else`; on hardware the constructor registers callbacks and does nothing else. However `Model.hpp` is *not* gated: it includes `SDK/RawTiles/Container.hpp` (Model.hpp:9) and holds an unconditional `SDK::RawTiles::Container mTiles;` member (Model.hpp:78) — so Container.cpp compiles and links into the ARM GUI ELF, it is just never opened. Net on-device behaviour: `mTiles.isOpen()==false` forever, TileCanvas draws slate.
- **RAWTILES_PATH hack — CONFIRMED** (Model.cpp:61-79): `std::getenv("RAWTILES_PATH")` wins; otherwise a 6-entry relative-path candidate walk (`kPackCandidates`, Model.cpp:25-32) covering the several working directories the simulator can be launched from — a workaround for the absence of any resource-lookup convention (§6).
- Viewport centre selection (Model.cpp:110-140): first index entry at `zoom_max` ("Earlier code used the median index, which … pushed the right two quadrants outside the pack", comment 121-123). Cache pool is a 4 KB static; `setCache` is called with a pre-counted `validCount` because "Passing numberOfDynamicBitmaps > bitmaps ever created leaves uninitialized metadata slots that corrupt the rendering pipeline" (Model.cpp:145-161) — a real TouchGFX footgun captured in code comments rather than in any doc.

### 4.3 Pack edges — CONFIRMED
Two mechanisms only: absent tiles are skipped at registration (Model.cpp:170-172), leaving `BITMAP_INVALID` slots that `TileCanvas::draw` skips (TileCanvas.cpp:58-60), exposing the slate background (cpp:25-30). There is no panning, no clamping, no reload — the viewport is chosen once in the Model constructor and never changes.

## 8. `SDK::TrackMapBuilder` (main) — CONFIRMED
`MAIN/Libs/Header/SDK/TrackMap/` — a breadcrumb-trail renderer: it projects the *recorded own-track* with a simple equirectangular projection (`kMetersPerDegree = 111320.0f`, TrackMapBuilder.cpp:194) into a small bitmap; **no file I/O, no tiles** (TrackMapBuilder.hpp:6,:23-24); `GpsPoint` is float lat/lon (:34-36). `TrackMapScreen::Point` is CONFIRMED **`struct { uint8_t x, y; }`** under `#pragma pack(push,1)` (`TrackMapScreen.hpp:27,:32-35`), with 255 a sentinel (usable range 0-254) — it targets a ≤255-px screen box and knows nothing about Mercator or zoom. Relationship to the map work: **they currently ignore each other** (CONFIRMED: RawTilesMap links TrackMapBuilder.cpp but has zero source references to it, §4.6). Compositionally they are complementary, not competing — TrackMapBuilder produces an overlay (where you went), RawTiles produces a basemap (where that was) — but composing them needs a shared geo→screen transform neither has (TrackMapBuilder normalizes track bbox to widget space with equirectangular scaling; the tiles are WebMercator; RawTiles has no coordinate math at all, §4.5). Nothing on the branch attempts it. Replace? No — neither subsumes the other; TrackMapBuilder can only ever be an overlay source over a tile basemap.

## 9. `SensorDataParserGpsLocation.hpp` (main) — CONFIRMED
Latitude/longitude/altitude are **float**, not double (`SensorDataParserGpsLocation.hpp:99-111,:88`) — and *structurally* so: the parser is a zero-copy view over `SensorDataView.hpp:26-35`, whose union has no double lane, so no parser change could recover doubles. ~7 significant digits ≈ 1.5 m position quantization. ## 12. Experiments-lineage lessons — CONFIRMED from commit bodies
The five most load-bearing design decisions mined from the ~45-commit `experiments` lineage:
1. `7ce54067` — **negative anchor coordinates are a framebuffer-underrun SIGSEGV, not a visual bug**: the naive "draw the 3×3 grid at a negative origin" first cut crashed outright; everything later (pre-clipping, blitRect discipline) descends from this.
2. `081c16ab` / `5381d01e` — **anchor semantics**: TouchGFX draws at the bitmap origin, not the clip-rect corner; getting this wrong mispositions every partially visible cell.
3. `19422afe` — **seam-centre selection**: the centre must be the *first* index entry at zoom_max, not the median; the median lands on `cx_max` for even-column packs and blacks out the right half of the viewport. The shipped code memorializes this verbatim (Model.cpp:117-123).
4. `99471a73` / `dfbc3ddf` — **orientation flip**: dynamic bitmaps skip imageconvert's pre-rotation, so external-bitmap content renders 90° CW unless the app commits to landscape end-to-end; hence the permanent `ORIENTATION_LANDSCAPE` setting that `7fc2602c`'s commit body explicitly defends ("a real, permanent setting, not part of that bug hunt").
5. `b07d33a4` → `e8a7eaf2` → `9712431d` — **the drawPartialBitmap→blitCopy pivot**: the first blitCopy attempt used an absolute rather than source-relative blitRect, "failed", and the approach was nearly abandoned for server-side composition before the corrected Experiment C2 vindicated it. (The shipped TileCanvas.cpp:48-54 comment and the Investigations bundle's C-vs-C2 pair are the fossil record.)
Supporting numbers from the lineage: RAM for the viewport went **96 KB → 640 KB** across the design, and the performance keystone is that pack bytes are TouchGFX-native ABGR2222 so rendering is zero-decode/zero-copy — both directly relevant to §7's device-RAM verdict.
Related dirty-rect lesson, CONFIRMED first-hand rather than from a single commit: a full repaint arrives as **11 separate dirty rects** and `draw(area)` must handle partial areas (Investigations logs/06; TileCanvas's per-cell intersection at TileCanvas.cpp:75-87 exists because of it), plus the cache-slot sizing trap (uninitialized dynamic-bitmap metadata slots corrupt rendering — Model.cpp:145-148).
One unreconciled discrepancy: `8897daf7` describes the pack as "12 tiles at z=12..14" while `19422afe` speaks of "2 columns × 3 rows at z=14" — consistent only if z14 holds 6 of the 12 tiles; the pack header (12 tiles, z∈[12,14], §14) permits that split but nothing verifies it. PLAUSIBLE; settled by running rawtiles_check's header dump per-zoom counts (Model's boot log also prints per-tile z/x/y).
