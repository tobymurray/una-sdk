# BacklightPwm results
#
# This app drives GPIOF PF3 directly, the pin the kernel uses as a plain
# on/off backlight enable. The ladder below asks for duty cycles the
# kernel's own REQUEST_BACKLIGHT_SET cannot produce.
#
# Compare against BacklightProbe's run at the same six values. There the
# registers were byte-identical at every brightness; here they should not
# be, and the light should step.
PWM start uptime_ms=35879 driving=Y
PWM core_clock_measured=160 MHz (cycles_per_us, from DWT_CYCCNT over a busy wait)
PWM period_us=4000 periods_per_burst=2 rungs=19
#
# kernel_writes counts bursts where GPIOF ODR disagreed with what this
# app last wrote. It is sampled just after our own write, so it catches
# a kernel that is winning the pin, not every kernel write: one landing
# between two of ours is overwritten within a millisecond and unseen.
# A zero count therefore means our writes dominate. Whether the light
# stayed lit through the contest rungs is the answer that counts.
PWM engine=timer+DMA TIM7 GPDMA_ch15
PWM rate first  arr=5000 spin=247 Hz
PWM rate final  arr=5038
PWM rate  spin        247 Hz  keeps up
PWM rate  yield       247 Hz  keeps up
PWM rate  1ms-naps    247 Hz  keeps up
PWM rate  long-sleep  7 Hz
PWM idle chosen=1ms-naps
#
# Those rates are counted passes of the waveform buffer over four
# tenths of a second of wall clock, read from the block-repeat counter
# the DMA keeps in hardware. They are measurements.
#
# spin never gives the core up, so it is the hardware's own rate with
# nothing gated, and every other mode is measured against it. Wherever a
# mode falls short, the waveform is stopped for the difference and the
# pin sits frozen at whatever the last word wrote. That reaches the eye
# as the light stuck full on or full off, not as a dimmer light, which
# is why a gated waveform looks worse than a slow one rather than the
# same. No choice of divider changes it.
#
# If only spin keeps up, an app can dim this light only by holding the
# core awake, and the DMA has bought nothing over a busy-wait. That is a
# finding about the kernel and the part, not about this app.
#
# On this engine 'achieved' is the duty the hardware was COMMANDED to
# produce, not a measurement: the duty is not counted, only the rate.
# The software engine's achieved figure is a measurement; this one is
# not, and they should not be compared.
